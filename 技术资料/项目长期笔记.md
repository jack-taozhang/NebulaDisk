## 项目本体

仿 Windows 云盘（NebulaDisk）+ kkFileView 合并镜像。

- 工作目录：`D:\Docker\kkFileView`
- 镜像：`nebula:1.0.0`（单容器双进程，supervisord 编排）
- 容器内：网关 `/opt/nebula/`（FastAPI :8088，**单 worker uvicorn**）；
  kkFileView `/opt/kkFileView-5.0.2/`（Java :8012）
- 宿主端口 8089 → 网关；测试凭据 `admin` / `Nebula@***`（Form 参数）
- **硬性要求：所有修复必须固化进镜像**，不许 `docker cp` 进运行中的容器。
- 环境：Docker 只能经 `wsl.exe -e docker` 访问；Git Bash 每次调用都要
  re-export PATH；heredoc 会吃掉 `'` 和 `$`，复杂脚本写成文件。
- 重建命令：`bash nebula/build.sh --up`
- 离线交付：`dist/nebula-1.0.0/`（tar + compose + install.sh + 安装说明），
  详见下文「离线部署包」一节。

**后端模块**（`nebula/app/`）：
`main.py` 路由/反代 · `config.py` 配置与映射解析 · `auth.py` 会话 JWT ·
`users.py` SQLite 用户库 · `files.py` 路径安全层 · `integrations.py`
OnlyOffice/kkFileView 对接 · **`shares.py` 分享（token 短链 + 密码 + 有效期/次数）**。


## ★ 架构铁律（违反会出整机故障）★

### 1. 网关是单 worker，响应路径上禁止任何阻塞 IO

supervisord 里 uvicorn 的启动参数**没有 `--workers`**，所以整个网关只有
一个事件循环。推论：

- 任何 `async def` 处理器里出现的**同步阻塞调用**（`httpx.Client`、
  `requests`、`time.sleep`、大文件读写、`subprocess.run`）都会冻结**全站**。
- 要慢操作就丢后台线程/进程，或用 `httpx.AsyncClient`。
- **`/healthz` 是纯内存接口**。它一旦变慢，只可能是事件循环被占死 ——
  这是最快、最准的诊断信号。

**真实事故（2026-09-20）**：为修 kkFileView 的压缩包缓存错位，在
`proxy_preview` 响应路径上加了同步的「探测 + 强制重解压」自愈
（最长阻塞 300s）。结果用户报告「预览压缩包时整个系统变得非常慢，
各个服务变成检查中」—— 单 worker 被解压占死，healthz 超时，
容器被判 unhealthy。**最终整体删除该逻辑**，不打补丁：收益（一个边角
404 场景）远小于风险（单点冻结全站）。

### 1.1 ★ 更要命的：那是**闭环死锁**，不只是变慢 ★

第一轮只看出「阻塞导致变慢」，实测才发现真相比这严重得多 ——
它是**网关与 kkFileView 互相等待的死锁**：

```
浏览器 → 网关 /preview/onlinePreview（压缩包）
           网关同步阻塞，等 kkFileView 解压完成（最长 300s）
         kkFileView 开始解压，但解压前必须先下载压缩包
           → GET http://nebula:8088/api/raw/xxx.zip   ← 打回网关！
           网关唯一的 worker 正卡在上面那步等待 → 无人应答
         ⏰ kkFileView DownloadUtils 读超时（30s）→ 下载失败
            → 解压失败 → 解压目录不存在 → 成员 404
```

**关键**：`/api/raw` 是**网关自己**的接口，而 kkFileView 必须经它取压缩包。
所以只要网关在等 kkFileView，kkFileView 就永远等不到网关 —— 闭环。

症状特征（实测数据，可直接对照）：
- `/onlinePreview` **每次都是精确的 30.1 秒**（不是解压耗时，是超时）
- 「第二次打开」也一样 30.1 秒（缓存根本没机会生效）
- `/directory` 的 `children` 恒为 `null`（解压从未成功）
- kkFileView 日志：`ResourceAccessException ... Read timed out`
  + `DownloadUtils 下载文件时发生未知异常`
- 成员 `getCorsFile` → **404**

**移除后的实测对比**（同一台机器、同样的两个包）：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| `/onlinePreview` 首次 | 30.10s | 2.75s / 0.19s |
| 第二次（走缓存） | 30.10s | 0.03s / 0.02s |
| `/directory` children | `null` | 非空 |
| 成员取字节 | 404 | 200（48.9MB / 3.7MB）|

**教训**：在反代层「等待后端完成某件事」时，必须先确认**后端完成这件事
是否需要回调本代理**。若是，就是闭环死锁，任何超时值都只是把死锁
变成慢+失败。诊断这类问题的利器是「耗时是否恰好等于某个超时值」。


### 2. 反代必须拆开「浏览器源」与「服务端源」

- `X-Base-Url` = **浏览器**访问源（**必须带端口**，否则预览页白屏）。
  绝不能用 `NEBULA_BASE_URL`（那是 `http://nebula:8088`，浏览器解析不了）。
- 服务端回拉（kkFileView 自己拉压缩包成员）用 `compress.ftl` 里的
  `__SERVER_BASE_URL__` 占位符，由网关替换成**容器内可达地址**。
- 两者职责分开，互不干扰。

### 3. URL 里的特殊字符必须编码

压缩包名可含 `#`（如 `1.2.14.TFDF-6# F向.zip`）。`#` 是 URL fragment 起点，
不编码会截断整条 URL，Java 侧抛
`URISyntaxException: Illegal character in fragment`。
模板侧用 `encodeMemberPath()`，网关侧对 query 里的
`kkCompressfilepath` / `urlPath` 再做一次 `#` → `%23` 兜底。

## 压缩包预览的已知行为

kkFileView `CompressFilePreviewImpl` 用**进程内缓存**（`cache.type=jdk`）
记「这个包已解压」，**key 只有文件名**，且**不校验解压产物目录是否还在**：

```java
if (forceUpdatedCache || !hasText(getConvertedFile(fileName)) || !isCacheEnabled()) {
    fileTree = compressFileReader.unRar(filePath, ...);      // 解压
    fileHandlerService.addConvertedFile(fileName, fileTree); // 记缓存
} else {
    fileTree = getConvertedFile(fileName);                   // 吃缓存，跳过 unRar
}
```

解压产物落在 `<fileDir>/<压缩包名>_/`。
⇒ 容器重建/清理后目录没了而缓存还在时，成员会 404。
**当前策略：不修**（网关侧修代价太大，见铁律 1）。
若将来要修，正确位置在**部署侧**：
启动时清解压产物目录 / 换 redis 外部缓存 / 先给 uvicorn 加 `--workers`。

**诊断探针**（确认解压目录真实存在）：
`/directory?urls=<base64 of "http://" + fileTree>`
→ `children` 非空 = 目录在；`children: null` = 「缓存说有、磁盘没有」。

**注意**：解压是**异步**的，48MB 的 `.stp` 要几十秒。
压缩包预览页返回 ≠ 成员已落盘。测成员前必须轮询 `/directory`
直到 `children` 非空，否则会稳定假报 404。

## 窗口管理器（WM）约定

`web/js/shell.js` 里有个 ~400 行的无边框窗口管理器。改窗口行为先读这里。

- 所有窗口都是 `chromeless: true`；工具栏 `.toolbar.win-toolbar`
  （带 `data-drag-handle`）兼作标题栏。`--toolbar-h: 29px`（app.css:63）。
- **resize 热区是 JS 动态生成的、样式全在 inline，CSS 里查不到**。
  8 个手柄 `['n','s','e','w','ne','nw','se','sw']`，
  `EDGE=14` / `CORNER=20` / `z-index:900`，`appendChild` 到 `.window`。
  想改外观只能改 `shell.js` 的 `_bindResize`。
- **窗口 id 粒度：一个映射一个窗口**，恒为 `explorer:<mount>`。
  `opts.newWindow` 分支已废除（双击文件夹曾错误地另开窗口）。
- **iframe 置顶必须「每次 load 后重绑」**：预览窗口内容是 `<iframe>`，
  点击内部不冒泡到父文档；且窗口打开时 iframe 还没 src（about:blank），
  真 src 加载会**换掉整个 document**，旧监听全丢。
  判重必须用「已绑定的 window 对象」（`__nebulaFocusWin`），
  不能用一次性布尔标志。几何兜底里 `state.el.contains(t)` 这个提前
  return 必须排除 `t.tagName === 'IFRAME'` 的情况。
- **三键 vs 热区冲突**：`.win-controls/.tb-controls` 是 `z-index:950`
  （高于热区 900）；JS 里 ne 角热区从 `top:var(--toolbar-h)` 开始、
  e 边接着下移。**`n` 边右端必须紧贴 `ne` 角（`right:20px`），不许为三键挖空**
  —— 挖空会在顶边留一条 ~110px 的死区（用户报的「调整大小有 BUG」）。
  三键优先命中靠的是 CSS 层级，不是靠热区让位。
  改热区尺寸时别把这条拆了。
- **热区必须严丝合缝铺满周长**：边厚一律 `EDGE`，边两端让位一律 `CORNER`，
  四角一律 `CORNER×CORNER`。混用 `EDGE`/`CORNER` 会让每条边两端各留
  `CORNER-EDGE`(=6px) 的缝。改 `EDGE`/`CORNER` 时要同步复核这四个角。
- ★ **拖动/缩放期间必须有整屏遮罩 `.wm-drag-shield` + 指针捕获** ★
  预览/编辑窗口 body 被 iframe 铺满。**指针一进入嵌套浏览上下文，父文档的
  `mousemove`/`mouseup` 就不再触发** → 拖动卡死、松手后还粘着鼠标。
  两道保险（各自都能独立解决）：
  1. `.wm-drag-shield`（`position:fixed;inset:0;z-index:9998`）拖动期间挂
     `document.body`，盖在所有 iframe 之上；
  2. `setPointerCapture(e.pointerId)` —— 规范保证被捕获元素收到全部指针事件。
  手势一律用 `pointerdown/pointermove/pointerup`，不要用 `mousedown/mousemove`。
  收尾函数挂到 `state._dragUp` / `state._resizeUp`，`close()` 里兜底撤除遮罩
  （否则拖到一半关窗会把遮罩永久留在屏上，吃掉全桌面点击）。
- **几何起点用 `_posOf()`，不要用 `offsetLeft/offsetTop`**：后者**取整**且
  相对 offsetParent。resize 会写出 `207.314px` 这种值，再用 `offsetLeft` 当
  基准就每次吃掉 <1px，反复拖动后可见偏移。`_posOf()` 用
  `getBoundingClientRect()` 减 `#window-layer` 的 rect，与 `style.left` 语义一致。
- **拖动钳位只有一个约束**：窗口与视口至少重叠 `KEEP=120px`（保证标题栏抓得住）。
  写回 `style.left/top` 时 `Math.round`。不要恢复成「多段不同上下限」的老写法，
  那种写法在边界上表现不一致、用户会以为是 bug。
- ★ **可用桌面高度 = `vh − taskbarH`，任何窗口尺寸/钳位都必须扣任务栏** ★
  `open()` 曾写 `Math.min(opts.height||620, vh - 24)` —— 只减 24px 边距，
  于是 600+ 高的窗口下边缘（含 `s`/`se`/`sw` 三个热区）**整条压在任务栏下面**，
  用户在那里按下去命中任务栏按钮而不是 resize 手柄。
  `--taskbar-h` 默认 48px 且随响应式断点变化，所以必须**实读 CSS 变量**，
  不能写死。涉及位置：`open()` 的 `H/X/Y/clX/clY`、拖动钳位的 `ny` 上限。
- **逐像素扫描热区时要 clamp 到可见交集**：`rect.bottom-3` 可能落在任务栏上；
  顶边扫到 `.tb-btn` 是**合法命中**（三键优先是设计），不要算成死区。
  权威判定还是看手柄的 CSS 几何是否「角↔边↔角」首尾相接。
- ★★★ **`.tb-btn` 与 `.tbtn` 是两套按钮，绝不能用同一个选择器一网打尽** ★★★
  这是本项目**反复出问题**的地方（两次真实故障都源于此）：

  | class | 谁产出 | 是谁 |
  |---|---|---|
  | `.tb-btn` + `data-act` | `Toolbar.build` 的三键模板 | 窗口控制键（最小化/最大化/关闭）|
  | `.tbtn` | `Toolbar.btn(...)` | 工具栏业务按钮（缩放/旋转/下载…）|
  | `.tb-btn nav-btn` | `viewer.js navBtns()` | **翻页键（看着像 tbtn，实际是 tb-btn！）**|

  - **故障一**：`_bindDrag` 的豁免判断写成 `closest('.tb-btn')`，
    只放过了三键 → `.tbtn` 业务按钮在 `pointerdown` 被 `preventDefault()`，
    浏览器不再派生 `click` → 「最顶上其它按钮全部失效」。
    修法：豁免选择器放宽到 `button, [role=button], input, textarea, select,
    a, [contenteditable], [data-no-drag]`。
  - **故障二**：`_bindControls` 用 `querySelectorAll('.tb-btn')` +
    监听里**无条件 `stopPropagation()`**，把翻页键（`.tb-btn.nav-btn`）
    也选中了 → 冒泡被掐断 → 「点『下一个文件』没反应」。
    修法：选择器收窄为 **`.tb-btn[data-act]`**。
  - **永久的规矩**：
    1) 给按钮挂"选择性"监听时，选择器必须带语义限定（`[data-act]`），
       不要用裸的 class；
    2) 监听里 `stopPropagation()` **必须放在确认这次点击真属于我之后**，
       不要写在函数第一行；
    3) 新增按钮前先确认它归哪一套 —— 尤其翻页键，它的 class 是
       `tb-btn nav-btn`（历史写法），**不要**把它当成 `.tbtn` 系列。
- ★★★ **预览窗口的「上一个/下一个」顺序必须与界面所见一致** ★★★
  界面渲染用 `explorer.js visibleEntries(S)`（文件夹优先 → 排序键 → 过滤），
  但 `S.entries` 是**接口原始顺序**。凡是要交给预览窗口做兄弟列表的，
  一律传 `visibleEntries(S)` —— 否则位置计数会出现「第 10 个文件写 20/25」
  这种对不上的数字，且「下一个」会跳到用户预料之外的文件。
  涉及三处：`Viewer.open` / `Viewer.openOnlyOffice` / `Viewer.refreshContext`。
- **预览窗口 id 不含文件路径**（`img:<mount>` / `kk:<mount>` / `oo:<mount>` /
  `cad:<mount>` / `text:<mount>` / `media:<mount>:<kind>`）。这是「原地换内容、
  不新开窗口」的前提。**副作用**：`WM.open` 的复用分支直接 `focus()` 早退、
  **不重渲染**，所以「先 `setContext(id, 新ctx)` 再 `WM.open`」会让
  **已显示的工具栏与 ctx 脱节**。翻页必须走 `Viewer.step` → `reopenInto`
  → `WM.reopen`（原地重渲染），不要靠"再 open 一次"。

## ★ 模块都在全局**词法**环境，不在 `window` 上 ★

`shell.js` / `viewer.js` / `icons.js` / `api.js` 全部是顶层 `const WM/Viewer/Icons/API = (() => {...})()`。
它们落在全局**词法**环境：**任何脚本都能用裸名访问**，
但 **`window.WM` / `window.Viewer` 是 `undefined`**（或空对象）。

- 浏览器探针里用 `WM.list()` / `Viewer.step(...)` **裸名**调用；
  写成 `window.Viewer.step` 会得到 `viewerKeys: []` 这种**假阴性**，
  从而把「逻辑正常」误判成「找不到函数」。

## ★ 测试铁律：抄逻辑的测试 = 没有测试 ★

`nebula/tools/_test_resize_hit.js` 曾把 `_bindResize` **抄**一份进测试，
抄的竟是过时参数（EDGE=10/CORNER=16）且没有让位逻辑 ——
**产品有 bug 它照样 12/12 全绿（假绿）**。

现在的做法（写 JS 测试时照抄这个模式）：
1. **读产品源码**，用花括号配平抽函数体，`new Function` 注入桩环境执行。
   产品改一行测试立刻跟着变，漂移不可能发生。
2. 加一段 **§0 源码同步性断言**（如 `/const EDGE\s*=\s*14/`）当总开关 ——
   抽取失败或抽到旧实现立刻报红。
3. 观测点必须是**产品真实写入的位置**。真实 `_bindResize` 只写
   `Object.assign(state.el.style,{left,top,width,height})`，
   **不写** `state._lastGeom` —— 那是旧测试自己造的虚构字段，
   断言它等于自娱自乐。改用 `geomOf(state)` 从 `el.style` 解析 px。
4. **负向断言前先 `stripComments()`**。本项目注释里写满「旧实现是错的」
   的说明文字，`!/newWindow:/` 这类断言会匹配到注释，产生**假红**。
5. **`dispatchEvent` 绕过命中测试**——合成事件会**直接投递给目标元素**，
   所以它永远"成功"。验证「用户到底能点到什么」必须用 `elementFromPoint`
   （或真实 CDP 鼠标）。热区死区就是这么才发现的。
6. **拖动与缩放的观测点不同**：缩放写 `left/top/width/height`，用 `geomOf()`；
   拖动**只写 `left/top`**，必须另用 `posOf()` —— 否则 `geomOf` 会因
   width/height 为空返回 null，误判成「没进入拖动态」（假红）。
7. DOM 桩要补齐：`className` setter 必须同步到 `classList`；
   `setPointerCapture/hasPointerCapture/releasePointerCapture` 三件套；
   `dispatch` 要自动带上 `target`（产品代码里有 `e.target.closest`）。
8. 测试若把两个 binder 放进**各自的 `new Function` 作用域**，模块级单例
   （如 `_shield`）会有多份 —— 断言要按「当前处于 `.on` 的那一个」筛选，
   不能盲取第一个（否则假红）。
9. **DOM 桩必须同时提供 `parent` 和 `parentNode`。** 真实 DOM 只有 `parentNode`；
   `_winOfNode` 是靠 `n = n.parentNode` 向上爬找 `dataset.winId` 的。
   桩里若只设 `parent`，链条第一跳就断 → `_winOfNode` 恒返回 `null` →
   归属判据退化成「z 序最高者」→ **看起来像产品 bug，其实是桩的锅**
   （`_test_iframe_focus.js` §8/§11 就这么假红过）。
10. **凡是走 `elementFromPoint` 桩的元素，都必须设 rect。** 零尺寸元素
   永远命不中 → `hit = null` → 走错分支。手搓 marker 时用
   `markerOf(id, x, y)` 这类助手自动给 2×2 的 rect。

## ★ 真实浏览器验证的三个致命陷阱 ★

纯逻辑测试全绿 **≠** 真实浏览器正确。反之，真实浏览器报红也 **≠** 产品有 bug。
本轮 `_ui_raise4.sh` 验证「点下层窗口置顶」时连踩三次，全部是**脚本自己的错**：

1. **绝不能手写 `zIndex`。** WM 的 `zTop` 从 **100** 起只增不减（shell.js:17），
   `focus()` 只会给出 101/102/103…。若在 JS 里把某窗口的 `zIndex` 写成字面量
   `"210"`，`focus()` **永远打不过它** → 必然假红。要**让产品自己的 `focus()`
   建立层叠序**（先点 A 再点 B 来安排上下关系）。
   （shell.js:913 的注释正好在讲这个坑。）
2. **摆窗口前先实测视口。** 本项目视口只有 **1264×625**（`--taskbar-h:48`）。
   曾有脚本摆了 900px 宽的窗口在 `x=520` → 右边界 1420 ≫ 1264，
   窗口被裁，且 `x>1264` 处 `elementFromPoint` 返回 `null`。
   脚本里要先读 `innerWidth/innerHeight` 与 `--taskbar-h`，在可见区内选坐标。
3. **探针坐标必须先经 `elementFromPoint` 验明归属**，再拿它去断言。
   `_raise_place3.js` 会打印每个探针点的 `aOnlyOwner/bOnlyOwner/overlapOwner`，
   归属不对就说明坐标选错了，别急着断产品。

### agent-browser 使用补充（0.38.1）

- **`eval` 返回的是 JSON 编码字符串**，引号带反斜杠：`"{\"ready\":true}"`。
  所以 `grep -q '"ready":true'` **永远匹配不到** → 会「明明就绪却判定未就绪」。
- ★ **正确的解法不是"用宽松正则"，而是"先去转义再精确匹配"** ★
  宽松式（`ready.*true`）会有**跨字段假命中**：
  整份 JSON 都在一行时，`probeBroken.*true` 会被后面的
  `"nextSwitches":true` 匹配到 —— 本轮就因此把一份**全绿**的探针结果
  误判成「未通过」。标准写法：
  ```bash
  V=$(runjs _probe.js)
  VC=$(printf '%s' "$V" | sed 's/\\"/"/g; s/\\\\/\\/g')   # 先去转义
  grep -qE '"probeBroken":true' <<<"$VC"                  # 再键值紧邻精确匹配
  ```
  判据统一用 `'"键":true'` 形式，**不要**用 `键.*true`。
- **不要在 `log "..."` 里做 `$(runjs ...)` 命令替换** —— 会卡死整个脚本。
  先 `V=$(runjs ...)` 再 `log "$V"`。
- **内联 JS 进 bash 的 `$( )` 极易与 heredoc/引号打架** → 每段 JS 写成独立
  `.js` 文件，`eval "$(cat file)"`。参考 `_ui_raise4.sh` + `_raise_*.js`。
- **一次调用里串联多个 `eval` 容易挂死**（此环境不稳）。
  实测「一个 bash 调用只做少量 eval」最可靠；整流程 ~2min，用后台跑。
- 新会话首次 eval 常返回空 → 要加**就绪闸门**：轮询 `#desktop-icons` 有子元素
  且 `#window-layer` 存在。
- 复跑要**幂等**：脚本开头先关掉残留窗口，否则 `window.__A/__B` 指向过期元素。
- ★ **探针自己也要自检** ★ 关键动作前后各放一个"必定有副作用"的对照动作
  （如点 `zoomin` 应改 `zlabel` 文本）。若对照都没反应，说明探针环境坏了，
  应报 `probeBroken` 并**拒绝给出结论**，而不是把环境问题当成产品 bug。
- ★ **`document` 捕获阶段收到事件 ≠ 目标能做响应** ★ 想判断"事件有没有到某个
  元素"，别只看 `document`；要在**那个元素本身**挂一个委托监听，
  或在沿途各层都挂，才能分清"没产生" / "被 stopPropagation 掐断" / "到了但分支没匹配"。

**本轮权威结论（已复现）**：两窗口重叠 A=[40,60,560,440]/B=[340,280,860,660]，
点 A 可见独占区 → `za 112→116`、`A_on_top:true`、B 不动。
**用户报的「点被挡住的窗口内部它不上来」确已修复。**

## ★ .dockerignore 的作用域规则（踩过一次，代价是每次构建白传 219MB）★

Docker 的 ignore 文件**只有两个位置会被读取**：

1. **上下文根**的 `.dockerignore` —— 对所有构建生效；
2. **`<Dockerfile 名>.dockerignore`**，与该 Dockerfile **同目录** ——
   只对这一个 Dockerfile 生效，且**优先级高于根那份**（不合并）。

子目录里随便放一个叫 `.dockerignore` 的文件 = **完全不被读取**。
本仓库曾把规则写成 `nebula/.dockerignore` → 一直失效 →
每次 `docker build` 都把 `nebula/sample/`(219MB)、`demo/`、`src/`、
还有 **`nebula/.env`（内含 OnlyKeys）** 全打包传给 daemon。

**现状（正确）**：
- 根 `.dockerignore`：只排「基础镜像构建 + 应用镜像构建**都不需要**」的东西
- `nebula/Dockerfile.dockerignore`：可以更激进，排掉只服务基础镜像的
  `src/ docker/ config/ demo/ nginx/`

⚠️ 反过来很危险：`nebula/.dockerignore` 的旧内容里排除了 `docker/`，
而**基础镜像构建恰恰需要 `docker/maven/settings.xml` 与 `docker/healthcheck.sh`**。
如果把那份规则直接抬到根 `.dockerignore`，基础镜像构建会坏。

**验证方法**（比读文档可靠）：
```bash
BUILDKIT_PROGRESS=plain docker build ... 2>&1 | grep 'transferring context'
# 期望 256.66kB 量级；若出现几百 MB，说明 ignore 没生效
```
`#4 transferring context: 256.66kB` 就是修好之后的实测值。

## 预览窗口两条不变量（2026-09-21 定稿，改动前务必先读）

### 不变量 1：翻页只在**同 kind** 内

`viewer.js` 的 `kindOf(entry, path)` 是唯一判据，取值
`'image'|'video'|'audio'|'text'|'cad'|'onlyoffice'|'kkfileview'|null`。
**判定顺序必须与 `open()` 的路由优先级严格一致**：
`route==='cad'` → `route==='onlyoffice'` → `nativeKind(ext)` → `route==='kkfileview'` → `null`。
不一致就会"判成一类、却由另一个引擎打开"。

接线点（漏一个就会退化）：
1. `makeCtx` — 算 `kind` 并用 `siblingsOfKind(all, kind)` 收窄列表，ctx 带 `kind`
2. `refreshContext` — `c.kind ? siblingsOfKind(entries, c.kind) : previewableList(entries)`
   （目录一刷新**不能退回宽列表**）
3. `step()` — 最后防线 `if (c.kind && kindOf(e) !== c.kind) return false;`

翻页列表的来源必须是 **`visibleEntries(S)`**（界面渲染用的那份：
文件夹优先 + 排序 + 过滤），**不是** API 原始顺序，也不是 `S.entries`。
三处调用点：`Viewer.open` / `Viewer.openOnlyOffice` / `Viewer.refreshContext`。

### 不变量 2：iframe 窗口靠**透明点击盾**置顶

OnlyOffice / CAD / kkFileView 的内容是 `<iframe>`：点在 iframe 内部时事件
被它自己的浏览上下文吃掉，**父文档收不到**；而 `focus`/`focusin` 只在焦点
**真正转移**时派发，所以第二次点同一处毫无反应。

解法：`shell.js` 在 iframe 上盖 `.iframe-shield`
（`position:absolute; inset:0; z-index:5; background:transparent; pointer-events:auto`），
它的 `mousedown` 必定冒泡到窗口 `el` 的捕获监听 → `focus(id)`。
- 非最顶层 → 盾 `auto`；置顶后 → 立即 `none`（否则内容点不动）
- 别的窗口置顶 → **全局** `focus()` 里 `_syncAllShields()` 重算所有窗口的盾
- sync 回调挂在模块级 `Set`（`_shieldSyncHooks`），**不要**每窗口一个 document 监听
  （那种写法重叠时会互相抢着置顶，是已被删掉的旧版缺陷）
- `attach()` 必须在 `makeShield`/`syncShield` **定义之后**调用（TDZ，否则开窗即崩）

窗口控制键监听只认 `.tb-btn[data-act]`（翻页键 class 是 `tb-btn nav-btn`，
被宽选择器吞掉过 click）。

## resize 热区设计（三轮收敛，别走回头路）

手感参数演进：5px（太薄，按不准）→ 14/20（太宽太快）→ **8/12 + 380ms 延时**。

```js
const EDGE = 8;                   // 边热区**窗内侧**厚度
const CORNER = 12;                // 角热区边长（必须 > EDGE，覆盖斜向）
const OUT = 4;                    // 热区向**窗口外侧**延伸的像素数
const RESIZE_HOVER_DELAY = 380;   // ms：停留满才显示 resize 光标
```

**hover intent 机制**（`_bindResize` 内）：
- 热区 initial cursor 是 `default`（inline 与 CSS 双写）
- `pointerenter` 起定时器；到期才 `armDir()` 挂 `<dir>-resize`
- `pointerleave` 立刻清定时器 + 光标回落
- 热区内 `pointermove` **不重置**定时器（手抖不该永远等不满）
- 换方向热区 → 先撤旧定时器再重新计时
- **`pointerdown` 无条件武装，不等延时** ← 关键：延时只影响光标提示，
  绝不拖慢真正的拖拽。改这段时务必保留这个语义。

**边缘几何不变量（2026-09-21 升级为「跨边框」）**：
热区**跨在窗口边框上** —— 外沿 = 窗口沿 ± OUT（向外伸），内沿 = 窗口沿 ∓ EDGE/CORNER。
- 定位助手：`OUT_N = -OUT + 'px'`、`span(len) = len + OUT + 'px'`
- 让位规则：**边让位用 CORNER、四角用 span(CORNER) = CORNER+OUT**
- ★★★ 最易错的点：让位量 `CLEAR = CORNER`，**不是** `CORNER + OUT` ★★★
  角是 `right:-OUT; width:CORNER+OUT` → 它**向内只盖到** `win.right-CORNER`；
  OUT 那截是往窗外去的。n/s 条的 `left/right` 量"从窗口内沿往内让多少"，
  只需让开角在窗内占的 CORNER。写成 `CORNER+OUT` 会留 **OUT=4px 的缝**。
- 唯一例外（不可消除）：`ne` 纵向从 `--toolbar-h` 起（给右上角三键让位）。
  这使 **右边 x=R 与右外侧带在 y∈[9,28] 无热区** —— 三键必须在那里赢。
- `n` 条右端可写到 `OUT_N`（直达右沿外），因为 ne 已下移、纵向与 n 条不重叠；
  这样**顶边全域零缝隙**。代价只是盖住三键顶部 12px，三键 `z-index:950` 仍赢。
- 全局必改项：`.window { overflow: visible }`（否则外扩被裁 = 白改），
  裁切职责下移到 `.toolbar`（上圆角）与 `.win-body`（下圆角）；
  另加 `.window.maximized [data-resize] { display: none }`。

**`close()` 必须清 hover 定时器**（`w._resizeHoverClear()`），
否则回调会去 query 一个已摘除的节点。

## ★ agent-browser / Windows 命令行三个致命坑（2026-09-21 全部实测）

1. **不要给 `agent-browser` 的输出接管道**（`agent-browser open ... | tail -3`）。
   实测接管道会让它**永久卡死**（stdout 被提前关闭导致写阻塞），
   超时后被杀，看起来像"浏览器坏了"。**一律重定向到文件**再读：
   ```bash
   abrun() { local tag="$1"; shift; $AB "$@" > "$TMPD/$tag.txt" 2>&1; }
   ```
   注意 `$AB` 变量**不能加引号**（它含空格，要按词拆分），
   否则报 `agent-browser --session xxx: command not found`。

2. **Windows 原生 curl 不认 MSYS 路径**（`/d/foo`）。
   传 `-c /d/.../jar.txt -o /d/.../out.json` 会报
   `curl: (23) client returned ERROR on write`，
   **并且不生成 cookie jar** → 会话拿不到票据 → 页面一直不 ready。
   必须先转 Windows 形式：
   ```bash
   winpath() { command -v cygpath >/dev/null 2>&1 && cygpath -m "$1" \
     || printf '%s' "$1" | sed -E 's#^/([a-zA-Z])/#\1:/#'; }
   ```
   另外 `-o /dev/null` 在这个 curl 上同样触发 exit 23，要写真实文件。

3. **`grep -q` + 进程替换 `<(...)` 会触发 SIGPIPE 卡死**。
   用 here-string：`grep -qE '"k":true' <<<"$V"`。

**探针环境自检**：`agent-browser doctor` 可快速判断浏览器是否健康
（`Headless launch + about:blank` 通过就说明浏览器没问题，问题在调用方式）。
清理会话：`agent-browser close --all`。
`~/.agent-browser/` 会攒大量 `*.port/*.pid/*.stream` 状态文件（本次 99 个会话）；
`E:/TEMP` 会攒 `agent-browser-chrome-*` profile 目录（本次 279 个）。
daemon 异常退出后会留下**指向死端口的 .port**，之后所有 `open` 都卡住 ——
删掉 `*.port/*.pid/*.stream` 即可恢复。

## 判据设计：几何归属 ≠ 功能正确

`_fs_probe.js` 一开始用 `elementFromPoint` 的归属（`owner === target.id`）
当主判据，结果重叠时上层窗口把整片区域盖住 → `mineCells:0` →
把**全绿**的结果判成失败。
正确判据：**直接看 zIndex 是否变大 / 是否成为最顶**，
与几何归属无关（"被盖住也能点上来"恰恰是点击盾要解决的问题）。
`elementFromPoint` 的归属只作诊断信息，不作断言。
