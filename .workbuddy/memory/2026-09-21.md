## 1. resize 热区：三轮用户反馈收敛

用户反馈演进（很重要，记录了取舍方向，别再走回头路）：
1. 早期：「调整大小需要按住才能调整」→ 热区太薄（5px）按不准 → 加宽到 **14/20**
2. 本轮：「感应范围感觉太快了，同时是不是可以增加一下 延时显示。」
   → 问题从"太薄"翻转成"太宽太快"
3. 本轮澄清：「感应范围太宽也太快。」「感应范围应该调整到窗口的边缘左右附近。」
   → 明确两件事：**几何要收窄** + **要延时** + **确认贴边缘**

### 1.1 几何收窄（EDGE 14→8，CORNER 20→12）

`shell.js` `_bindResize`：
```js
const EDGE = 8;       // 边热区厚度（14 → 8）
const CORNER = 12;    // 角热区边长（20 → 12）
```
- 仍 > 最初的 5px（保留下界，不重蹈"按不准"）
- 角仍 > 边（斜向缩放捕获区更大）
- **让位规则不变**：边让位用 CORNER、四角 CORNER×CORNER —— 这才是周长零缝隙的保证
  （若让位误用 EDGE，角与边之间会露 CORNER-EDGE 的空档 → 抓不到）

### 1.2 延时显示（hover intent）—— 本次核心新机制

新增常量 `RESIZE_HOVER_DELAY = 380`（用户说"太快"，从 260 提到 380）。

机制（`_bindResize` 内，每个窗口一份 `hover` 状态）：
| 事件 | 行为 |
|---|---|
| `pointerenter` | `clearHover()` → 起 380ms 定时器 |
| 定时器到期 | 若热区还在且窗口未最大化 → `armDir(dir)` |
| `pointerleave` | `clearHover()` + 光标回落 `default` |
| 热区内 `pointermove` | **不重置**定时器（否则手抖永远等不满） |
| 换到别的方向热区 | 先撤销旧定时器再重新计时 |
| `pointerdown` | **无条件** `armDir(dir)`，不等延时 |

`armDir(dir)` 做三件事：`el.style.cursor = '<dir>-resize'`、
`el.dataset.armed = '1'`、`document.body.style.cursor = '<dir>-resize'`。

**关键设计取舍：延时只作用于"光标提示"，绝不延迟真正的拖拽。**
急着拖的用户体感零延迟，只是不会在半路被光标闪到。

配套改动：
- 热区 inline `cursor` 从 `` `${dir}-resize` `` 改为 `'default'`
- CSS 加 `[data-resize] { cursor: default; }` 兜底（JS 未跑时不退化成旧行为）
- `up()` 里 `resetCursors()` + `state._resizing = false`
- `close()` 里加 `w._resizeHoverClear()` 兜底清定时器

### 1.3 边缘定位实测（回答"应该调整到窗口的边缘附近"）

写了 `_hz2_probe.js` 用**直接读 `getBoundingClientRect()`** 的方式量热区
相对窗口边缘的位置（不靠 elementFromPoint 命中，避免被窗口遮挡干扰）。

真机实测结果（窗口 1100×550，border 1px，radius 8px）：
```
gap.e_right = -1    gap.w_left = 1     gap.n_top = 1     gap.s_bottom = -1
gap.ne_right = -1   gap.sw_left = 1    gap.sw_bottom = -1
gap.ne_top = 30   ← 故意：为右上角三键让位（--toolbar-h = 29px）
overflow = []     ← 无越界
eastScanHits = ",e,e,e,e,e,e,e,e,"  ← 从右沿往里连续 8px 命中 e 手柄
```
结论：**热区本来就精确贴在窗口边缘**（差值 ±1px 正是 1px 边框），
用户感知到的"偏内"很可能来自窗口圆角 / iframe 内容自带边距的视觉错觉。
本轮把厚度从 14 收到 8 后，边缘感会更明确。

## 5. Request D：热区**跨边框**（感应区伸出窗口外）

用户原文：
> 「调整窗口 鼠标感应 区域 以边框外边缘 向左和向右，向上向下偏移一定范围内
>   都可激活。目前都是在窗口里面，这个要调整一下。」

### 改动（`nebula/web/js/shell.js`）
- 新增 `const OUT = 4`（向**窗口外侧**延伸的像素数，`EDGE/CORNER` 仍是内侧厚度）。
- 两个助手：`OUT_N = -OUT + 'px'`（外沿偏移）、`span(len) = len + OUT + 'px'`（跨边框尺寸）。
- 8 个手柄全部改为 `left/right/top/bottom = OUT_N` + `width/height = span(...)`。
- ★★ 关键坑：`const CLEAR = CORNER + 'px'`（**不是** `CORNER + OUT`）★★
  角是 `right:-OUT; width:CORNER+OUT` → 它**向内只盖到** `win.right-CORNER`，
  外沿那 OUT 是往窗外去的。而 n/s 条的 `left/right` 量的是"从窗口内沿往内让多少"，

- ★ n 条右端改为 `right = OUT_N`（直达右沿外）★
  因为 ne 角纵向已下移到 `--toolbar-h`，与 n 条（y∈[-4,8]）**不重叠**，
  n 伸过去不抢 ne；代价是盖住三键顶部 12px，但三键 `z-index:950` 仍赢。

- 裁切职责下移：`.toolbar { border-radius: 上两角; overflow:hidden }`、

- 新增 `.window.maximized [data-resize] { display: none }`（最大化时铺满视口，

## 6. 分享功能（Request E1）

用户诉求：「增加分享功能」。落地为**面向访客的 token 短链分享**。

### 数据层 `nebula/app/shares.py`（新）
- 表 `shares`：`token / owner / mount / path / name / is_dir / password /
  created_at / expires_at / max_visits / visits / note`，唯一索引 `idx_shares_owner`
- token = `secrets.token_urlsafe(24)`（32 字符）；**库里存明文 token**
  —— 刻意选择，因为 token 本身就是 URL 里的凭据，存哈希只会增加一次查表；
  安全性靠「32 字符不可枚举」+ 可随时撤销，不是靠不可逆
- 密码：可选，存 **bcrypt 哈希**（复用 `users.hash_password`）
- `ttl<=0` → `expires_at = 0` 表示永不过期（而不是 `now+0`）
- `revoke_under_path(owner, mount, path)`：`path = ? OR path LIKE pref+'/%'`
  —— 用 `pref + '/%'` 而不是 `pref + '%'`，否则 `/dir/a` 会误伤 `/dir/abc`

### 接口层 `nebula/app/main.py`
- 登录侧：`GET/POST /api/shares`、`/api/shares/revoke`、`/api/shares/update`
- 访客侧（**不挂 `current_user` 依赖**）：`GET /api/s/{token}`（返回 HTML）、
  `POST /api/s/{token}/unlock`、`GET /api/s/{token}/list`、
  `GET /api/s/{token}/raw`、`GET /api/s/{token}/preview`、
  `GET /api/s/{token}/sraw/{filename}`、`POST /api/s/{token}/oo-callback`
- 公开短链：`GET /s/{token}`

### 三个关键设计决定
1. **权限继承**：创建时用**创建者**的权限集校验 `(mount, path)`；
   访客访问时复用**分享者**作为可见性上下文（`_mount_for_share`），
   而不是按访客身份判断——访客可能根本没有账号。
2. **解锁凭据不是密码**：`POST /unlock` 成功后写 HttpOnly Cookie
   `nebula_share_<token[:16]>`，值 = `sha256(password_hash + token)`。
   即「解锁凭证」而非密码本身，泄露该 Cookie 也拿不到密码。
3. **给访客的 raw 链接必须自签名**：OnlyOffice / kkFileView 是**服务端**去
   GET 文档的，带不了访客的 Cookie。所以另发
   `/api/s/{token}/sraw/{filename}?token=&path=&exp=&sig=`，
   `sig = HMAC(jwt_secret, "share\n{token}\n{sub}\n{exp}")`。

### 穿越防护（双重）
访客给的 `path` 是**相对分享根**的子路径 → 先 `files.resolve()` 展开校验，
再 `_inside_share(m, p, sh)` 二次确认结果仍在分享根之内。

### 前端
- `web/share.html` + `web/css/share.css` + `web/js/share.js`：**独立自洽**的
  访客落地页（跟随 `prefers-color-scheme`），服务端把 `window.__SHARE__`
  注入到 `__SHARE_BOOT__` 占位符
- 云盘侧：`explorer.js` 加右键「分享」/「分享此文件夹」/「管理我的分享…」，
  新增 `icons.js` 的 `share:` 图标与 `api.js` 的四个封装

### 验证
- `nebula/tools/_test_shares.py`（新）：**48 通过 / 0 失败**，
  覆盖穿越拒绝（`../secret.txt` 等）、伪造 token、跨 owner 撤销被拒、
  owner 隔离、不泄露 password 字段、过期/超次、删除源文件→分享自动失效、
  前缀匹配不过宽（`/dir/abc` 不被 `/dir/a` 误伤）
- `selfcheck.py` 新增 `[9] 分享（安全边界）`（~24 条），路由清单扩到 **30 条**

## 7. 清理冗余 + 离线镜像包（Request E2/E3）

### 7.1 踩到的真坑：`nebula/.dockerignore` 一直是**失效**的
Docker 只读「上下文根」的 `.dockerignore`；想针对某个 Dockerfile 单独排除，
必须命名为 `<Dockerfile 名>.dockerignore` 并放在该 Dockerfile **同目录**。
原名 `nebula/.dockerignore` 名字不对 → daemon 根本不读 →
每次 `docker build` 都把 `sample/`(219MB)、`docs/`、`tools/`、`nebula/.env`
一起打包传给 daemon（慢，且把本地密钥带进构建上下文）。

修法（双保险）：
- 改名 `nebula/.dockerignore` → **`nebula/Dockerfile.dockerignore`**
- 上下文根 `.dockerignore` 补齐「两个构建都不需要」的条目
  （`nebula/sample|data|data-kk|tools|docs|.env*|selfcheck*|*.md`、`.workbuddy/`、`dist/`）

实测证据（`BUILDKIT_PROGRESS=plain`）：
`#4 transferring context: 256.66kB` —— 与之相对，修之前会把 219MB 全传。

> 注意：上下文根 = 仓库根，**两个 Dockerfile 共用**。所以根 `.dockerignore`
> 只能排除「A 基础镜像构建、B 应用镜像构建都不需要」的东西；
> 只对 B 多余但 A 需要的（`src/`、`docker/`）必须留给
> `nebula/Dockerfile.dockerignore` 排除。反过来 `nebula/.dockerignore` 旧内容
> 里排除了 `docker/` —— 若它真生效反而会把基础镜像构建搞坏。

  - 删 101 项：cookie jar（`_ck*.txt`）、探针日志（`*.out`）、临时目录

### 10.4 ★ 本轮抓到的真 bug：`docker compose -f` 不叠加默认文件 ★

我最初在 `install.sh` 里写成：

```bash
CAD_FLAG="-f docker-compose.cad.yml"
$COMPOSE $CAD_FLAG up -d        # ✗ 错
```

**教训**：用假 docker 演练时，光看退出码不够 —— 必须让假 docker
**把收到的参数记下来**再断言。这次就是靠 `DOCKER_CALL: compose -f …`
那一行才抓出来的。

## 12. 换机器部署后 OnlyOffice「打开文件时发生错误」

用户报障：在其他电脑上部署，点开文档弹
「错误 / 打开文件时发生错误 / 点击"确定"关闭错误。」

### 12.1 ★ 关键判读方法（一条就能砍掉 90% 的排查面）★

> 编辑器**外壳**（工具栏、页码 1/2、缩放 100%）能渲染出来
> ⇒ 配置下发与 JWT **都是通的**；
> 只有**正文**打不开
> ⇒ 失败发生在「**OnlyOffice 服务端去 GET 文档**」这一步。

所以排查范围天然缩小到「**网络能不能互通 + 地址填得对不对**」，
与 JWT、与前端、与文件本身**都无关**。
（反过来说：如果连编辑器外壳都出不来，那才是 JWT/配置问题，是另一类故障。）

### 12.2 本机基线（证明「配置是对的」长什么样）

| 项 | 值 |
|---|---|
| OO 容器 | `maple-onlyoffice`，网络 `deploy_default`（172.19.0.3） |
| nebula 容器 | 网络 `deploy_default`（172.19.0.5）+ `nebula_default` |
| `NEBULA_BASE_URL` | `http://nebula:8088` |
| `NEBULA_OO_URL` | `http://maple-onlyoffice` |
| JWT | 两边都是 `dev-oo-secret-for-local-testing-only` |
| OO `default.json` | `request-filtering-agent.allowPrivateIPAddress = **false**` |
| 决定性检查 | 在 OO 容器内 `curl http://nebula:8088/healthz` → **200** |

**注意**：本机 `allowPrivateIPAddress` 是 **false**（没开私有 IP 放行），
但走**主机名** `nebula` 却完全正常 —— 说明这个过滤器拦的是
**IP 字面量**（`http://172.19.0.5:8088` 这种），主机名不受影响。
所以**不要**为了让 CAD/OO 工作去盲目开这个开关，先确认地址用的是主机名。

### 12.3 根因排序（换机器部署场景）

1. **两个容器不在同一 docker 网络**（最可能）
   - 我这边的 `install.sh` 建了一个**占位空网络** `nebula-oo`，
     而 `.env.example` 默认 `NB_OO_NETWORK=nebula-oo`
   - → OnlyOffice **不在**这个网络上 → 解析不了 `nebula` → 必然报这个错
   - 这是我给的默认值埋的坑，已在 §12.4 修掉
2. `NEBULA_BASE_URL` 未设置 → 回退 `http://127.0.0.1:8088`（OO 自己的 localhost）
3. `NB_BASE_URL` 用了 **IP 字面量** → 触发 OO 的私有 IP 过滤器
   （日志：`DNS lookup ... is not allowed. Because, It is private IP address.`）
4. `NB_BASE_URL` 写成宿主机端口 `:8089`（应该用容器端口 `:8088`）
5. 两边 `JWT_SECRET` 不一致（但这种通常外壳也出不来，与本现象不同）

### 12.4 本轮做的修复（都在 `dist/nebula-1.0.0/`）

## 13. ★ 真根因：OO 的 converter 以 `ds` 非 root 用户跑，`/tmp` 必须世界可写 ★

用户贴出了真正的日志（比我上一轮基于截图的推断有用得多）：

```
[ERROR] ... receiveTask Error: EACCES: permission denied,
  mkdir '/tmp/ASC_CONVERT2026821-1trh0ad.9kxp'
  at getTempDir (server/FileConverter/sources/converter.js)
```

⇒ **与网络完全无关**（他们三个服务都在 `nebula-net` 上）。
我上一轮「两个容器不在同一网络」的判断在这个案例里是**错的**。

### 13.1 定位过程（关键是别测错对象）

1. 先看进程用户 —— **决定性发现**：
   `/etc/supervisor/conf.d/ds-converter.conf` 里 `user=ds`，
   运行态 `ps` 显示 `converter`/`docservice` 都是 **`ds`(uid=101, gid=102)**，
   只有 `allthemesgen` 是 root。
2. **我第一次探测全错了**：用 `docker run ... sh -c 'mkdir /tmp/x'` 时
   entrypoint 默认以 **root** 跑（`id -u` = 0），四种 tmpfs 写法全部通过。
   必须加 `--user ds` 才是被测对象。
   （顺带：`docker run` 若不加 `--entrypoint`，`sh -c ...` 会被镜像的
   `ENTRYPOINT /app/ds/run-document-server.sh` 当成参数吃掉，
   结果把整套 DS 启起来、`--rm` 永不返回。用 `--entrypoint sh`。）
3. 以 `ds` 重测，触发条件就唯一了：

| `/tmp` 挂载方式 | 结果 |
|---|---|
| 不挂 tmpfs（镜像默认） | `drwxrwxrwt 0:0` → **mkdir OK** |
| `uid=1000,gid=1000`（mode 缺省或 1777） | `drwxrwxrwt 1000:1000` → **mkdir OK** |
| `mode=0755` | `drwxr-xr-x` → **EACCES** |
| `mode=1755` | `drwxr-xr-t` → **EACCES** |
| `ro` | → **EACCES** |

   ⇒ **只要 `/tmp` 的 other 段没有 `w`+`x`，或只读，`ds` 就写不进去。**
   注意 `uid=1000,gid=1000` 本身**不是**问题（mode 仍是 1777）；
   问题在于那台 NAS 上 `mode=1777` 没被正确应用
   （图形化容器管理器把 mode 按十进制解析后重写成别的权限是常见原因）。
4. **答案其实早就写在项目里**：`D:\DwgViewer\deploy\docker-compose.yml`
   的 onlyoffice 注释里已经写明
   「`/tmp` 不映射，保持容器内默认（1777，人人可写）」以及
   「勾了『只读根文件系统』或指定了用户 → FileConverter 报
   `EACCES mkdir /tmp/ASC_CONVERT*`」。
   本机可用的那份：`HostConfig.Tmpfs = null`、`/tmp` = `drwxrwxrwt 0:0`。
   **→ 遇到同类问题先翻项目里已经能用的那份配置。**

### 13.2 宿主目录 vs 命名卷：实测对照（这条是硬结论，不是预防性建议）

OO 的 `/var/www/onlyoffice/Data` 在镜像里是 `drwxrwsr-x 101:102`（ds 可写）。
挂宿主目录会把镜像自带的属主**整个盖掉**：

| 挂法 | 结果 |
|---|---|
| 宿主目录 bind（`./onlyoffice/data:/var/www/onlyoffice/Data`） | `drwxr-xr-x 0:0` → **ds 不可写** |
| 命名卷（`oo-data:/var/www/onlyoffice/Data`） | `drwxrwsr-x 101:102` → **ds 可写** |

（命名卷由 Docker 用镜像内容+属主初始化；宿主目录不会。）
⇒ OO 的四个数据目录**必须用命名卷**，尤其在 NAS 上。

`dist/nebula-1.0.0/docker-compose.allinone.yml`
（+ 副本到 `D:\Docker\nebuladisk\`）—— 保持用户原有的路径/账号/端口，
只改 OO 那几处：

### 14.2 ★ 真根因：镜像自带的 /tmp 就是 0755 ★

```
  → drwxr-xr-x 1 1001 1002  /tmp        ← 不是 drwxrwxrwt！
```

| 环境 | digest | 镜像自带 /tmp |
|---|---|---|
| 开发机（`/d/Docker`） | `141847e5…` | `drwxrwxrwt 0:0` ✅ |
| 目标 NAS | `3ab6ebc7…` | **`drwxr-xr-x 1001:1002`** ❌ |

⇒ 目标机上那份**被重打过**（大小也略有差异）。**同一个 tag，digest 不同，内容就会不同。**

### 14.3 ★ 第二个坑：这台 NAS 的 Docker，tmpfs 默认 mode 是 0755 ★

在 NAS 上以 `ds` 实测（`docker run --user ds --entrypoint sh … mkdir /tmp/x`）：

| `/tmp` 挂法 | 结果 | |
|---|---|---|
| 镜像自带 | `drwxr-xr-x 1001:1002` | ❌ |
| `tmpfs: /tmp`（不写 mode） | `drwxr-xr-x 0:0` | ❌ |
| `tmpfs: /tmp:size=2G`（不写 mode） | `drwxr-xr-x 0:0` | ❌ |
| `tmpfs: /tmp:mode=1777` | `drwxrwxrwt 0:0` | ✅ |
| `uid=1000,gid=1000,mode=1777` | `drwxrwxrwt 1000:1000` | ✅ |

⇒ **必须显式写 `mode=1777`**。裸 `/tmp` 或只写 `size` 都不行 —— 因为这台 NAS 的

## 15. 点「最顶上的工具栏」也要能前置窗口（两种窗口）

用户原文：
> 「窗口点击聚焦显示所有窗口 最顶上的工具栏（最小化，最大化，关闭这一行）
>   目前没有涵盖在呢。需要增加点击这个区域也能前置显示窗口。两种窗口都要修改。」

### 15.1 根因：置顶只挂在 `mousedown` 上，而 pointerdown 会把它掐掉

- 置顶原本只有一条路：`attach()` 里
  `el.addEventListener('mousedown', () => focus(id), true)`。
- 但 `_bindDrag`（工具栏整条是拖动区）在 pointerdown 末尾会
  `if (e.cancelable) e.preventDefault();`（为抑制文本选择 / touch 滚动）。
- 按 **Pointer Events 规范，在 pointerdown 上 preventDefault 会一并抑制
  浏览器派生的 `mousedown`** ⇒ 这条链上根本没有 mousedown ⇒ 点工具栏不置顶。
- 只有点**内容区**（不 preventDefault 的路径）才置顶 —— 与用户描述完全吻合。

> 同一个机制在 `_bindDrag` 的注释里**已经为业务按钮踩过一次**，那次是反面：
> preventDefault 让 `button` 的 `click` 也不触发（「按钮全失效」）。
> 这次是它把 `mousedown` 掐掉了。**同一条 preventDefault，两种伤害。**

### 15.2 改了两处（一处覆盖两种窗口，另一处必须单独补）

| 位置 | 改动 | 为什么在这里 |
|---|---|---|
| `_bindDrag` pointerdown | 在**按钮豁免与 preventDefault 之前**加 `focus(state.id)` | explorer 手写工具栏与预览窗口 `WM.Toolbar.build` 共用同一个 `.toolbar.win-toolbar[data-drag-handle]`，一处改两种窗口都生效 |
| `_bindResize` pointerdown | 同样在 preventDefault 前加 `focus(state.id)` | 热区是 `.window` 的**直接子元素、不在工具栏里**，工具栏那处覆盖不到；且它还会 `stopPropagation()` |

两个「必须在之前」的理由：
- 在**按钮豁免之前** → 三键与所有业务按钮点下去也要先浮到最上层（Windows 行为）；
- 在 `if (state.maximized) return` 之前 → **最大化着的后台窗口点标题栏也该前置**。

安全性核对：`focus()` = `_raise`（只发新 z 号）+ 切 `.focused` + `_syncTaskbar`
+ `_syncAllShields`，幂等；`opts.onFocus` 目前**没有消费者**，不会触发重渲染。

顺带修正 `explorer.js` 里一条**过时注释**（还写着旧判据 `closest('.tb-btn')`，
会误导后续改动）。

### 16.4 三条硬教训（已写进 `~/.workbuddy/MEMORY.md`）
1. **这个环境永远不要用 `pip --force-reinstall`** —— 守卫会把它掐成半截，
   而且残骸伪装成"能 import"。要升级就用 `--upgrade`，或"新鲜目录 + 覆盖复制"。
2. **传给原生 Windows 程序的路径必须写 `C:/...`**，`/c/...` 会被当成
   「当前盘根下的 c 目录」（实测装到了 `C:\c\Users\...`）。
   踩过：`pip --target`、`curl -o`、`python <脚本>`。
3. **`sysconfig.get_paths()` 在 base 解释器里指的是 base 自己** ——
   用它当解压目标会把包装进 base 而非 venv；目标路径要写死明确。
