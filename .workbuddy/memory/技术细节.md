## 1. 压缩包预览：闭环死锁事故全记录（2026-09-20）

### 故障链条

```
浏览器 → 网关 /preview/onlinePreview（压缩包）
           网关同步阻塞，等 kkFileView 解压完成（最长 300s）
         kkFileView 开始解压，但解压前必须先下载压缩包
           → GET http://nebula:8088/api/raw/xxx.zip   ← 打回网关！
           网关唯一的 worker 正卡在上面那步等待 → 无人应答
         ⏰ kkFileView DownloadUtils 读超时（30s）→ 下载失败
            → 解压失败 → 解压目录不存在 → 成员 404
```

`/api/raw` 是**网关自己**的接口，kkFileView 必须经它取压缩包 → 只要网关在等 kkFileView，
kkFileView 就永远等不到网关 = **闭环**。

### 移除前后实测对比（同机同样两个包）

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| `/onlinePreview` 首次 | 30.10s | 2.75s / 0.19s |
| 第二次（走缓存） | 30.10s | 0.03s / 0.02s |
| `/directory` children | `null` | 非空 |
| 成员取字节 | 404 | 200（48.9MB / 3.7MB）|

### kkFileView 缓存实现（`CompressFilePreviewImpl`）

```java
if (forceUpdatedCache || !hasText(getConvertedFile(fileName)) || !isCacheEnabled()) {
    fileTree = compressFileReader.unRar(filePath, ...);      // 解压
    fileHandlerService.addConvertedFile(fileName, fileTree); // 记缓存
} else {
    fileTree = getConvertedFile(fileName);                   // 吃缓存，跳过 unRar
}
```

`cache.type=jdk`（进程内），**key 只有文件名**，**不校验解压产物目录是否还在**。
解压产物落在 `<fileDir>/<压缩包名>_/`。

**诊断探针**：`/directory?urls=<base64 of "http://" + fileTree>`
→ `children` 非空 = 目录在；`children: null` = 「缓存说有、磁盘没有」。

**注意**：解压是**异步**的，48MB 的 `.stp` 要几十秒。压缩包预览页返回 ≠ 成员已落盘。
测成员前必须轮询 `/directory` 直到 `children` 非空，否则会稳定假报 404。

## 2. WM 细节（补 `MEMORY.md` 的 WM 速记）

- `shell.js` 里的无边框 WM 是**一个文件 ~1900 行**，改窗口行为先读它
- resize 手柄：8 个 `['n','s','e','w','ne','nw','se','sw']`，`appendChild` 到 `.window`，
  样式全 inline
- **iframe 置顶重绑的完整逻辑**：点击 iframe 内部不冒泡到父文档；且窗口打开时 iframe 还是
  `about:blank`，真 src 加载会**换掉整个 document**，旧监听全丢。
  ⇒ 判重必须用「已绑定的 window 对象」（`__nebulaFocusWin`），不能用一次性布尔标志；
  几何兜底里 `state.el.contains(t)` 的提前 return 必须排除 `t.tagName === 'IFRAME'`
- **三键 vs 热区的正确修法**：`.win-controls/.tb-controls` 是 `z-index:950`（> 热区 900）；
  JS 里 ne 角热区从 `top:var(--toolbar-h)` 开始、e 边接着下移。
  **`n` 边右端必须紧贴 `ne` 角（`right:20px`），不许为三键挖空** —— 挖空会在顶边留一条
  ~110px 死区（用户报的「调整大小有 BUG」）。三键优先命中靠 CSS 层级，不是靠热区让位。
- **热区严丝合缝铺满周长**：边厚一律 `EDGE`，边两端让位一律 `CORNER`，四角一律 `CORNER×CORNER`。
  混用 `EDGE`/`CORNER` 会让每条边两端各留 `CORNER-EDGE`(= 6px 或 4px) 的缝。
  改 `EDGE`/`CORNER` 时同步复核这四个角
- **拖动钳位只有一个约束**：窗口与视口至少重叠 `KEEP=120px`（保证标题栏抓得住）。
  不要恢复成「多段不同上下限」的老写法
- **可用桌面高度 = `vh − taskbarH`**：`open()` 曾写 `Math.min(opts.height||620, vh - 24)`，
  于是 600+ 高的窗口下边缘（含 `s`/`se`/`sw` 三个热区）**整条压在任务栏下面**，
  用户在那里按下去命中任务栏按钮而不是 resize 手柄

## 3. resize 热区设计（三轮收敛，别走回头路）

手感参数演进：5px（太薄，按不准）→ 14/20（太宽太快）→ **8/12 + 380ms 延时**。

```js
const EDGE = 8;                   // 边热区**窗内侧**厚度
const CORNER = 12;                // 角热区边长（必须 > EDGE，覆盖斜向）
const OUT = 4;                    // 热区向**窗口外侧**延伸的像素数
const RESIZE_HOVER_DELAY = 380;   // ms：停留满才显示 resize 光标
```

**hover intent 机制**（`_bindResize` 内）：

- 热区 initial cursor 是 `default`（inline 与 CSS 双写）
- `pointerenter` 起定时器；到期才 `armDir()` 挂 `<dir>-resize`
- `pointerleave` 立刻清定时器 + 光标回落
- 热区内 `pointermove` **不重置**定时器（手抖不该永远等不满）
- 换方向热区 → 先撤旧定时器再重新计时
- **`pointerdown` 无条件武装，不等延时** ← 关键：延时只影响光标提示，
  绝不拖慢真正的拖拽。改这段时务必保留这个语义

**边缘几何不变量（2026-09-21 升级为「跨边框」）**：热区**跨在窗口边框上** ——
外沿 = 窗口沿 ± OUT（向外伸），内沿 = 窗口沿 ∓ EDGE/CORNER。

- 定位助手：`OUT_N = -OUT + 'px'`、`span(len) = len + OUT + 'px'`
- 让位规则：**边让位用 CORNER、四角用 span(CORNER) = CORNER+OUT**
- ★★★ 最易错的点：让位量 `CLEAR = CORNER`，**不是** `CORNER + OUT` ★★★
  角是 `right:-OUT; width:CORNER+OUT` → 它**向内只盖到** `win.right-CORNER`；
  OUT 那截是往窗外去的。n/s 条的 `left/right` 量"从窗口内沿往内让多少"，
  只需让开角在窗内占的 CORNER。写成 `CORNER+OUT` 会留 **OUT=4px 的缝**
- 唯一例外（不可消除）：`ne` 纵向从 `--toolbar-h` 起（给右上角三键让位）。
  这使 **右边 x=R 与右外侧带在 y∈[9,28] 无热区** —— 三键必须在那里赢
- `n` 条右端可写到 `OUT_N`（直达右沿外），因为 ne 已下移、纵向与 n 条不重叠；
  这样**顶边全域零缝隙**。代价只是盖住三键顶部 12px，三键 `z-index:950` 仍赢
- 全局必改项：`.window { overflow: visible }`（否则外扩被裁 = 白改），
  裁切职责下移到 `.toolbar`（上圆角）与 `.win-body`（下圆角）；
  另加 `.window.maximized [data-resize] { display: none }`
- **`close()` 必须清 hover 定时器**（`w._resizeHoverClear()`），
  否则回调会去 query 一个已摘除的节点

## 4. 测试铁律完整版

### 4.1 抄逻辑的测试 = 没有测试

`nebula/tools/_test_resize_hit.js` 曾把 `_bindResize` **抄**一份进测试，
抄的竟是过时参数（EDGE=10/CORNER=16）且没有让位逻辑 ——
**产品有 bug 它照样 12/12 全绿（假绿）**。

现在做法（写 JS 测试时照抄这个模式）：

1. **读产品源码**，用花括号配平抽函数体，`new Function` 注入桩环境执行。
   产品改一行测试立刻跟着变，漂移不可能发生
2. 加一段 **§0 源码同步性断言**（如 `/const EDGE\s*=\s*8/`）当总开关 ——
   抽取失败或抽到旧实现立刻报红
3. 观测点必须是**产品真实写入的位置**。真实 `_bindResize` 只写
   `Object.assign(state.el.style,{left,top,width,height})`，**不写** `state._lastGeom` ——
   那是旧测试自己造的虚构字段，断言它等于自娱自乐。改用 `geomOf(state)` 从 `el.style` 解析 px
4. **负向断言前先 `stripComments()`**。本项目注释里写满「旧实现是错的」的说明文字，
   `!/newWindow:/` 这类断言会匹配到注释，产生**假红**
5. **`dispatchEvent` 绕过命中测试** —— 合成事件会**直接投递给目标元素**，所以它永远"成功"。
   验证「用户到底能点到什么」必须用 `elementFromPoint`（或真实 CDP 鼠标）。热区死区就是这么才发现的
6. **拖动与缩放的观测点不同**：缩放写 `left/top/width/height`，用 `geomOf()`；
   拖动**只写 `left/top`**，必须另用 `posOf()` —— 否则 `geomOf` 会因 width/height 为空返回 null，
   误判成「没进入拖动态」（假红）
7. DOM 桩要补齐：`className` setter 必须同步到 `classList`；
   `setPointerCapture/hasPointerCapture/releasePointerCapture` 三件套；
   `dispatch` 要自动带上 `target`（产品代码里有 `e.target.closest`）
8. 测试若把两个 binder 放进**各自的 `new Function` 作用域**，模块级单例（如 `_shield`）
   会有多份 —— 断言要按「当前处于 `.on` 的那一个」筛选，不能盲取第一个（否则假红）
9. **DOM 桩必须同时提供 `parent` 和 `parentNode`。** 真实 DOM 只有 `parentNode`；
   `_winOfNode` 是靠 `n = n.parentNode` 向上爬找 `dataset.winId` 的。桩里若只设 `parent`，
   链条第一跳就断 → `_winOfNode` 恒返回 `null` → 归属判据退化成「z 序最高者」→
   **看起来像产品 bug，其实是桩的锅**（`_test_iframe_focus.js` §8/§11 就这么假红过）
10. **凡是走 `elementFromPoint` 桩的元素，都必须设 rect。** 零尺寸元素永远命不中 →
    `hit = null` → 走错分支。手搓 marker 时用 `markerOf(id, x, y)` 这类助手自动给 2×2 的 rect
11. **测试桩四条补充铁律**：z 号走**计数器**（等价 `_raise`），**别手写** `zIndex`；
    `CSSStyleDeclaration` 桩要能接 **`cssText`** 写入并解析成属性；
    `vm` 抽函数时它引用的**模块级 `let`** 必须一并注入沙箱；
    写**区间**断言（`EDGE>=6 && EDGE<=10`）而非等值断言

### 4.2 真实浏览器验证的三个致命陷阱

纯逻辑测试全绿 **≠** 真实浏览器正确。反之，真实浏览器报红也 **≠** 产品有 bug。
`_ui_raise4.sh` 验证「点下层窗口置顶」时连踩三次，全部是**脚本自己的错**：

1. **绝不能手写 `zIndex`。** WM 的 `zTop` 从 **100** 起只增不减（shell.js:17），
   `focus()` 只会给出 101/102/103…。若在 JS 里把某窗口的 `zIndex` 写成字面量 `"210"`，
   `focus()` **永远打不过它** → 必然假红。要**让产品自己的 `focus()` 建立层叠序**
   （先点 A 再点 B 来安排上下关系）。（shell.js:913 的注释正好在讲这个坑）
2. **摆窗口前先实测视口。** 本项目视口只有 **1264×625**（`--taskbar-h:48`）。
   曾有脚本摆了 900px 宽的窗口在 `x=520` → 右边界 1420 ≫ 1264，窗口被裁，
   且 `x>1264` 处 `elementFromPoint` 返回 `null`。脚本里要先读 `innerWidth/innerHeight`
   与 `--taskbar-h`，在可见区内选坐标
3. **探针坐标必须先经 `elementFromPoint` 验明归属**，再拿它去断言。
   `_raise_place3.js` 会打印每个探针点的 `aOnlyOwner/bOnlyOwner/overlapOwner`，
   归属不对就说明坐标选错了，别急着断产品

**权威结论（已复现）**：两窗口重叠 A=[40,60,560,440]/B=[340,280,860,660]，
点 A 可见独占区 → `za 112→116`、`A_on_top:true`、B 不动。
**用户报的「点被挡住的窗口内部它不上来」确已修复。**

### 4.3 判据设计：几何归属 ≠ 功能正确

`_fs_probe.js` 一开始用 `elementFromPoint` 的归属（`owner === target.id`）当主判据，
结果重叠时上层窗口把整片区域盖住 → `mineCells:0` → 把**全绿**的结果判成失败。
正确判据：**直接看 zIndex 是否变大 / 是否成为最顶**，与几何归属无关
（"被盖住也能点上来"恰恰是点击盾要解决的问题）。
`elementFromPoint` 的归属只作诊断信息，不作断言。

### 4.4 `run_unit_tests.sh` 的坑（都写进了脚本注释）

- `mktemp -d` 在 Git Bash 返回 MSYS 路径，**Windows 原生 node.exe 读不到**
  → 用脚本同级 `.unit_tmp/`
- `$HERE` 也是 MSYS 路径 → 传给 node 前必须 `winpath()`
- 汇总行**两种语序**都要匹配：`13 通过 / 0 失败`（数在前）与 `通过 12 / 12`（数在后）；
  「零失败」的写法也有 `全部通过`/`0 失败`/`失败 0` 三种

### 4.5 探针 runner 四条铁律

1. **JS 一律走 heredoc**（`node - ... <<'JS' … JS`）。
   内联 `node -e '...'` 时，JS 里只要出现 `'`（哪怕在注释里），bash 引号配对
   就错位 → 报一个**与真实位置无关**的 "unexpected EOF"（曾指向文件末行）
2. **JSON 路径键名是字符串契约**：探针叫 `gaps.*`/`innerThickness.*`，
   runner 写成 `gap.*`/`inner.*` → 12 个字段全"无法解析"假红
3. 取数组用 **`JSON.stringify`**，不能用 `String()`（`[[8,37]]` 被压成 `"8,37"`）。
   ★ 而且 `String(["a","b"])` 出来是 **`a,b`（逗号连接、无空格）**，
   所以 `for tok in $OV` 会**把整串当成一个词** → 必须先 `tr ',' ' '` 再遍历
4. **`set -u` 下引用未赋值变量会当场崩掉整个 runner**（曾以 `NE_ALLOW: unbound variable`
   在第 115 行终止，把后面检查全带没了）。凡是「上限/阈值」都不要写死裸变量，
   要么现算（如从探针报出的 `toolbarH` 推 `NE_ALLOW = toolbarH + 12`），要么给默认值兜底

## 5. agent-browser 使用补充（0.38.1）

- ★ **正确的解法不是"用宽松正则"，而是"先去转义再精确匹配"** ★
  宽松式（`ready.*true`）会有**跨字段假命中**：整份 JSON 都在一行时，
  `probeBroken.*true` 会被后面的 `"nextSwitches":true` 匹配到 —— 本轮就因此把一份**全绿**的
  探针结果误判成「未通过」。标准写法：
  ```bash
  V=$(runjs _probe.js)
  VC=$(printf '%s' "$V" | sed 's/\\"/"/g; s/\\\\/\\/g')   # 先去转义
  grep -qE '"probeBroken":true' <<<"$VC"                  # 再键值紧邻精确匹配
  ```
  判据统一用 `'"键":true'` 形式，**不要**用 `键.*true`
- **不要在 `log "..."` 里做 `$(runjs ...)` 命令替换** —— 会卡死整个脚本。
  先 `V=$(runjs ...)` 再 `log "$V"`
- **内联 JS 进 bash 的 `$( )` 极易与 heredoc/引号打架** → 每段 JS 写成独立
  `.js` 文件，`eval "$(cat file)"`。参考 `_ui_raise4.sh` + `_raise_*.js`
- **一次调用里串联多个 `eval` 容易挂死**（此环境不稳）。
  实测「一个 bash 调用只做少量 eval」最可靠；整流程 ~2min，用后台跑
- 新会话首次 eval 常返回空 → 要加**就绪闸门**：轮询 `#desktop-icons` 有子元素
  且 `#window-layer` 存在
- 复跑要**幂等**：脚本开头先关掉残留窗口，否则 `window.__A/__B` 指向过期元素
- ★ **探针自己也要自检** ★ 关键动作前后各放一个"必定有副作用"的对照动作
  （如点 `zoomin` 应改 `zlabel` 文本）。若对照都没反应，说明探针环境坏了，
  应报 `probeBroken` 并**拒绝给出结论**，而不是把环境问题当成产品 bug
- ★ **`document` 捕获阶段收到事件 ≠ 目标能做响应** ★ 想判断"事件有没有到某个
  元素"，别只看 `document`；要在**那个元素本身**挂一个委托监听，
  或在沿途各层都挂，才能分清"没产生" / "被 stopPropagation 掐断" / "到了但分支没匹配"

### 三个致命坑（实测）

1. **不要给 `agent-browser` 的输出接管道**（`agent-browser open ... | tail -3`）。
   实测接管道会让它**永久卡死**（stdout 被提前关闭导致写阻塞），
   超时后被杀，看起来像"浏览器坏了"。**一律重定向到文件**再读：
   ```bash
   abrun() { local tag="$1"; shift; $AB "$@" > "$TMPD/$tag.txt" 2>&1; }
   ```
   注意 `$AB` 变量**不能加引号**（它含空格，要按词拆分），否则报
   `agent-browser --session xxx: command not found`
2. **Windows 原生 curl 不认 MSYS 路径**（`/d/foo`）。
   传 `-c /d/.../jar.txt -o /d/.../out.json` 会报
   `curl: (23) client returned ERROR on write`，**并且不生成 cookie jar**
   → 会话拿不到票据 → 页面一直不 ready。必须先转 Windows 形式：
   ```bash
   winpath() { command -v cygpath >/dev/null 2>&1 && cygpath -m "$1" \
     || printf '%s' "$1" | sed -E 's#^/([a-zA-Z])/#\1:/#'; }
   ```
   另外 `-o /dev/null` 在这个 curl 上同样触发 exit 23，要写真实文件
3. **`grep -q` + 进程替换 `<(...)` 会触发 SIGPIPE 卡死**。
   用 here-string：`grep -qE '"k":true' <<<"$V"`

**探针环境自检**：`agent-browser doctor` 可快速判断浏览器是否健康
（`Headless launch + about:blank` 通过就说明浏览器没问题，问题在调用方式）。
清理会话：`agent-browser close --all`。
`~/.agent-browser/` 会攒大量 `*.port/*.pid/*.stream` 状态文件（本次 99 个会话）；
`E:/TEMP` 会攒 `agent-browser-chrome-*` profile 目录（本次 279 个）。
daemon 异常退出后会留下**指向死端口的 .port**，之后所有 `open` 都卡住 ——
删掉 `*.port/*.pid/*.stream` 即可恢复。

| 1 | 两容器不在同一 docker 网络（最常见） | OO 必须能解析 `nebula`；容器名只有**同网络**才解析得到。`NB_OO_NETWORK` 必须是 OO **真正所在**的网络名。⚠️ `install.sh` 建的 `nebula-oo` 是**占位空网络**（只为让 `external` 不报错） |
| 2 | `NEBULA_BASE_URL` 未设置 | 回退 `127.0.0.1:8088`（OO 自己的 localhost） |
| 3 | 用了 **IP 字面量** | 撞 OO 私有 IP 过滤器：`DNS lookup ... is not allowed. Because, It is private IP address.`。★ 实测 `allowPrivateIPAddress=false` 时**主机名照样能用**，它拦的是 IP 字面量，别急着改这个开关 |
| 4 | 写成宿主机端口 `:8089` | 容器间互通要用容器端口 `:8088` |
| 5 | 两侧 `JWT_SECRET` 不一致 | 通常外壳也出不来，属另一类 |

### 6.2 类 B：转换失败（本地 IO/权限）

```
ERROR ... receiveTask Error: EACCES: permission denied,
  mkdir '/tmp/ASC_CONVERT2026xxxx-xxxx'
  at getTempDir (server/FileConverter/sources/converter.js)
```

**根因**：OO 的 `converter`/`docservice` **以非 root 用户 `ds`(uid=101) 运行**
（`/etc/supervisor/conf.d/ds-converter.conf` 里 `user=ds`），
它要在 `/tmp` 下建临时目录，所以 **`/tmp` 必须世界可写**（other 位要有 w+x）。

**★★ 结论（2026-09-21 TPNAS 实地修正，此前那条是错的）★★**

**正确做法：给 `/tmp` 挂 tmpfs，并显式写 `mode=1777`。**

```yaml
    tmpfs:
      - /tmp:rw,exec,size=2G,mode=1777
```

1. **同一个 `onlyoffice/documentserver:latest` 标签，不同机器上 digest 不同、
   镜像自带 `/tmp` 也不同**：
   - 开发机 `141847e5…` → 镜像自带 `drwxrwxrwt 0:0`（不挂 tmpfs 也能用）
   - 目标 NAS `3ab6ebc7…` → 镜像自带 **`drwxr-xr-x 1001:1002`**（错的，被重打过）
   ⇒ 「/tmp 用镜像自带的就行」**不能作为通用建议**
2. **有些 NAS 的 Docker 给 tmpfs 的默认 mode 是 0755，不是标准 Docker 的 1777。**
   所以**不能**简写成 `- /tmp` 或 `- /tmp:size=2G` —— 实测两者得到的仍是
   `drwxr-xr-x`，`ds` 照样写不进去。**必须带 `mode=1777`**

TPNAS 上以 `ds` 实测（`docker run --user ds --entrypoint sh … mkdir /tmp/x`）：

| `/tmp` 挂法 | 结果 |
|---|---|
| 镜像自带 | `drwxr-xr-x 1001:1002` ❌ |
| `tmpfs: /tmp`（不写 mode） | `drwxr-xr-x 0:0` ❌ |
| `tmpfs: /tmp:size=2G`（不写 mode） | `drwxr-xr-x 0:0` ❌ |
| `tmpfs: /tmp:mode=1777` | `drwxrwxrwt 0:0` ✅ |

**区分是镜像问题还是运行时被改**：
`docker run --rm --entrypoint sh <OO镜像> -c 'ls -ldn /tmp'` ——
不是 `drwxrwxrwt` 就是**镜像自身**的问题。
（另：`docker run` 不加 `--entrypoint` 时 `sh -c …` 会被镜像 ENTRYPOINT 吃掉、
`--rm` 永不返回；且**必须带 `--user ds`**，用 root 测四种写法全过，会得出错误结论。）

**数据目录**：宿主目录绑定不是绝对不行，**看属主**。
TPNAS 上实测 `/var/www/onlyoffice/Data` 与 `/var/lib/onlyoffice` 属主都是
`101:102` → ds 可写，够用。若属主是 `root:root 755`（很常见），宿主目录绑定会
**盖掉**镜像自带属主 → ds 不可写；此时改用命名卷
（命名卷由 Docker 用「镜像内容 + 属主」初始化，实测得 `drwxrwsr-x 101:102`）。
判定：`docker exec <oo> ls -ldn <目录>` 看属主是不是 `ds`/`101:102`。

### 6.3 端到端自测（不用等人点文档）

拿到 OO 的 JWT 密钥后，对 `{"payload": {...}}` 做 HS256 签名、塞进 body 的 `token`，
POST `http://127.0.0.1/converter`；返回
`{"fileUrl":"…output.pdf","percent":100,"endConvert":true}` 即整条链路通。

### 6.4 本机实测通过的完整链路

2026-09-21 在 TPNAS 上实测：`/tmp`=drwxrwxrwt、`ds` mkdir OK、

## 10. 预览窗口两条不变量（改动前务必先读）

### 不变量 1：翻页只在**同 kind** 内

`viewer.js` 的 `kindOf(entry, path)` 是唯一判据，取值
`'image'|'video'|'audio'|'text'|'cad'|'onlyoffice'|'kkfileview'|null`。
**判定顺序必须与 `open()` 的路由优先级严格一致**：
`route==='cad'` → `route==='onlyoffice'` → `nativeKind(ext)` → `route==='kkfileview'` → `null`。
不一致就会"判成一类、却由另一个引擎打开"。

接线点（漏一个就会退化）：

1. `makeCtx` — 算 `kind` 并用 `siblingsOfKind(all, kind)` 收窄列表，ctx 带 `kind`
2. `refreshContext` — `c.kind ? siblingsOfKind(entries, c.kind) : previewableList(entries)`
   （目录一刷新**不能退回宽列表**）
3. `step()` — 最后防线 `if (c.kind && kindOf(e) !== c.kind) return false;`

翻页列表的来源必须是 **`visibleEntries(S)`**（界面渲染用的那份：文件夹优先 + 排序 + 过滤），
**不是** API 原始顺序，也不是 `S.entries`。
三处调用点：`Viewer.open` / `Viewer.openOnlyOffice` / `Viewer.refreshContext`。

### 不变量 2：iframe 窗口靠**透明点击盾**置顶

OnlyOffice / CAD / kkFileView 的内容是 `<iframe>`：点在 iframe 内部时事件
被它自己的浏览上下文吃掉，**父文档收不到**；而 `focus`/`focusin` 只在焦点
**真正转移**时派发，所以第二次点同一处毫无反应。

解法：`shell.js` 在 iframe 上盖 `.iframe-shield`
（`position:absolute; inset:0; z-index:5; background:transparent; pointer-events:auto`），
它的 `mousedown` 必定冒泡到窗口 `el` 的捕获监听 → `focus(id)`。

- 非最顶层 → 盾 `auto`；置顶后 → 立即 `none`（否则内容点不动）
- 别的窗口置顶 → **全局** `focus()` 里 `_syncAllShields()` 重算所有窗口的盾
- sync 回调挂在模块级 `Set`（`_shieldSyncHooks`），**不要**每窗口一个 document 监听
  （那种写法重叠时会互相抢着置顶，是已被删掉的旧版缺陷）
- `attach()` 必须在 `makeShield`/`syncShield` **定义之后**调用（TDZ，否则开窗即崩）

窗口控制键监听只认 `.tb-btn[data-act]`（翻页键 class 是 `tb-btn nav-btn`，
被宽选择器吞掉过 click）。
